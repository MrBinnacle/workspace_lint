# v0.1 hydration map — what each rule must fetch, and what a partial fetch does to it

**Class:** slice spec. Same evidence tier as `docs/adr/`, differing in scope, not authority. It
**decides nothing new**: every row below follows from a rule's own definition in `CONTEXT.md`, from
the settled default that the block crawl is selective, and from decisions already accepted in
ADR-0005, ADR-0006, ADR-0007, ADR-0011, ADR-0012, ADR-0013 and ADR-0014. Where this file and an ADR
disagree, **the ADR wins and this file is the defect**. Edited in place.

**Issue:** #18. **Marked revisable** where it makes a slice-scoping choice; there is one, in §1.3.

**What this file is not.** It is not a performance budget for an implementation, and it is not a
claim about how fast a scan runs. It states what each rule **must** read to reach a judgement, and
what its evidence sufficiency becomes when it reads less.

---

## 1. The map

Read the last column first. The fetch depth is the cheap half; what a shortfall does to the rule's
evidence sufficiency is the half that decides whether the rule can ship.

| Rule | Coverage item (ADR-0011) | Minimum fetch depth | Pagination to completion | Endpoint attestation |
| --- | --- | --- | --- | --- |
| `SYS001` | resource | existence of the resource | **required** | `unattested` |
| `REF001` | internal reference | **nested block content** | **required** | `unattested` |
| `REQ001` | (resource, required property) pair | page properties | **required** over the scope | `unattested` |
| `UNQ001` | unordered pair of resources in a uniqueness scope | page properties | **required**, and see §1.4 | `unattested` |

Every endpoint the v0.1 scan calls is `unattested` — `GET /v1/blocks/{id}/children` carries no
truncation signal (ADR-0006 decision 2, strengthened to an enumerated SDK omission by ADR-0007
decision 5), and neither `GET /v1/pages/{id}` nor `GET /v1/users/me` enumerates anything. The one
`attested` endpoint this project has classified is `POST /v1/search`, and **v0.1 does not call it**
(ADR-0014 decision 1). See §4.

### 1.1 `SYS001` — a declared root or applicable resource was not evaluated

**Depth: existence.** The declared root is retrieved with `GET /v1/pages/{id}`. Descendants are not
retrieved to be counted — they arrive as `child_page` and `child_database` blocks inside their
parent's block listing, which is why `SYS001` needs the traversal spine and nothing deeper.

**Pagination: required.** An abandoned pagination is an **unbounded** gap under ADR-0005 decision 5,
and the manifest records boundedness as structure written by the losing site, never inferred from a
cause string.

**Partial hydration:** the resource is `unreached`, and `SYS001` reports it with
`Certainty: confirmed`. That is not a contradiction of `CONTEXT.md`'s *"a 404 produces
`indeterminate`"* — `SYS001` asserts a proposition about **the scan** (*this resource was not
evaluated*), which the manifest proves, where `REF001` asserts a proposition about **a target**,
which a 404 does not prove.

### 1.2 `REF001` — internal target is archived, in Trash, or unreachable

**Depth: nested block content.** The deepest of the four, and the one that sets the budget. Links
live inside blocks, blocks nest, and a link inside a toggle inside a column is a link the rule must
see. Descent follows `has_children`.

**Resolution costs one request per unique target.** Targets deduplicate on the resolved ID, so a
page carrying fifty links to one dead target resolves it once — observed, `docs/proof/results-t3-ref001.md`
§3. This is also why the coverage item is the **target** and not the link instance: the ratio must
not swing on how many times an editor pasted the same URL.

**Pagination: required**, both over a resource's block list and over every nested list beneath it.

**Partial hydration is the most consequential case in this file.** References inside unread blocks
are never enumerated, so the shortfall does not appear as a missing answer — it appears as a
**smaller denominator**. The run reports a reference ratio over the references it happened to find.
Because `GET /v1/blocks/{id}/children` is `unattested`, the scan cannot know it happened, and by
ADR-0013 the unattested enumeration is a **named residual**, not a Gap: it enters no ratio, no
vector and no pervasiveness test. `REF001` is the load-bearing coverage mechanism, so this is where a
silent hydration shortfall does the most damage and where the residual register earns its existence.

### 1.3 `REQ001` — a selected resource lacks a required property value

**Depth: page properties.** `GET /v1/pages/:id` returns `properties` at `Notion-Version:
2026-03-11` — `docs/research/notion-api-documented.md`, the `GET /v1/pages/:id` response field list.
No block content is required. `REQ001` is the shallowest of the four.

**Revisable — the acquisition route.** Two routes return the same field:

1. **N × `GET /v1/pages/{id}`**, one per in-scope resource.
2. **`POST /v1/data_sources/{id}/query`**, paginated, returning page objects with their properties —
   roughly one request per 100 rows.

Route 2 is an order of magnitude cheaper for a data-source-backed scope and is the recommended
default. It is marked revisable rather than settled because no run has exercised it: the 2026-08-17
proof run called the query endpoint, but for enumeration, not for property hydration. *Revisit if:*
#58's build shows the query response does not carry the property shape the rule needs, or the scope
is not data-source-backed, in which case route 1 is the only route.

**Pagination: required over the scope.** `scope` is a required key on a `REQ001` config entry and
the absence of a default is deliberate — a required-property rule with no scope would assert the
property over every enumerated resource, inferring applicability from nothing, which ADR-0001
decision 4 rejects.

**Partial hydration has a second, sharper failure than a short scope.** The vendor's request-size
limits cap **relations at 100 related pages and people fields at 100 users** *per single request*
(`docs/research/notion-api-documented.md` §2, "Size limits"). A `REQ001` over a relation or people
property can therefore read a **truncated value inside an otherwise successful response**. The rule
must not read a truncated non-empty value as present-and-complete, and must never read a truncated
value as absent. That read is unattested, so under ADR-0013 it is a **residual**, not a violation —
*no call, no residual* is the rule, and here there is no call to make. This is a consequence of
ADR-0013 decision 2, not a new decision, and it is recorded here because #58 will meet it first.

### 1.4 `UNQ001` — a declared unique value occurs more than once

**Depth: page properties**, identical to `REQ001`, and the same two acquisition routes apply.

**Pagination: required, and this one is arithmetic rather than policy.** A uniqueness claim over a
partly enumerated scope is unsound **in the flattering direction**: the duplicate lives in the unread
tail, so a short read reports uniqueness it did not establish. `CONTEXT.md` supplies the shape of the
loss — at 90% of resources read, `UNQ001` has evaluated **80.9%** of the pairs it quantifies over,
because the coverage item is a pair and pairs fall off quadratically.

**Partial hydration:** the applicable set of pairs shrinks, the residual register names the
enumeration that was not attested, and no duplicate may be reported as absent. `UNQ001` is the rule
for which a partial scan most resembles a clean one.

### 1.5 The four deferred rules

One line each, so the map does not have to be rebuilt when they ship. **None has a coverage item
assigned, and this file does not assign one** — `CONTEXT.md` requires each to declare its own before
it is built.

| Rule | Minimum fetch depth |
| --- | --- |
| `SCH001` — peer data sources have incompatible schemas | data-source metadata (the `properties` schema). No page content. |
| `REL001` — a relation violates its allowed target contract | data-source metadata **and** page properties: the contract is in the schema, the violation is in the value. |
| `DEP001` — an active resource points to an inactive dependency | page properties, **plus** the target's own state — the same per-target resolution cost `REF001` pays. |
| `CAN001` — a boundary contains more than one explicit canonical marker | page properties across the boundary; the boundary definition is undecided and may force block content. |

## 2. The budget

**540 requests.** Notion documents *"an average of three requests per second, with some bursts
beyond the average allowed"* per connection (`docs/research/notion-api-documented.md` §2, "Documented
limits"). `PRODUCT.md`'s kill criteria set the ceiling: *"A warm scan exceeds three minutes on the
reference scope after selective hydration."* Three minutes at three requests per second is roughly
540 requests. **A hydration map that cannot fit a reference workspace inside that budget is a failed
map, not a slow one.**

**Pacing is open-loop.** No rate-limit-state headers exist — only `Retry-After`, after the fact
(`docs/research/notion-api-documented.md` §2, "Headers reporting limit state — a documented gap"). A
scanner cannot observe its remaining budget; it can only be told, once, that it has already exceeded
it. Anything that reacts to a 429 is reacting to a limit it has already hit.

**Both numbers are borrowed and both invalidate everything below.** *Revisit if:* the documented
rate changes, or the three-minute criterion moves. Either one moves every estimate in §3, not just
the total.

## 3. The worked estimate

### 3.1 The cost formula

For one run:

```
R  =  1                                    GET /v1/users/me
   +  D                                    GET /v1/pages/{id}, one per declared root
   +  Σ_resources  ceil(children / 100)    the traversal spine          [SYS001]
   +  Σ_blocks_with_children ceil(...)     recursive descent            [REF001]
   +  U                                    unique internal targets      [REF001]
   +  P                                    property hydration           [REQ001, UNQ001]
```

`P` is `|scope|` under acquisition route 1, or `Σ ceil(rows / 100)` under route 2 (§1.3).

### 3.2 The formula reproduces the only run this project has observed

Fixture shape: `D = 1`; three enumerated resources; one of them (`wl-pagination`) holding 151 blocks
and so costing two pages; no block carrying `has_children`; one unique internal target.

```
1 (whoami) + 1 (root) + 4 (root + 2 pagination pages + wl-revoke-parent) + 0 (descent) + 1 (target) + 0 = 7
```

**Observed: 7 requests, 1872 ms** — `docs/proof/results-t3-ref001.md` §3, which prints the call log.
The formula is validated against one run at n=1 and nothing larger. Every figure in §3.3 is
**extrapolation from that single observation** and is labelled so rather than presented as an
estimate.

### 3.3 Two shapes, and the term that decides

| Shape | Resources | Blocks/resource | Blocks with children | Unique targets | `P` | **R** |
| --- | --- | --- | --- | --- | --- | --- |
| **B** — small real workspace | 150 | 10 | 8% (120) | 40 | 3 (one 300-row data source, route 2) | **~315** |
| **C** — same workspace, deeper content | 150 | 10 | 20% (300) | 40 | 3 | **~495** |

Shape B fits. Shape C fits and has no margin. Change nothing but nesting depth and the budget is
spent.

**The finding: the budget is bound by block-tree shape, not by workspace size.** The resource count
contributes one request per resource. The recursive descent contributes one per block that has
children, and that term is unbounded in the *shape* of the content rather than in the count of
resources. A single page can dominate a whole run.

**Corroborating, and lower-tier.** A widely cited third-party figure: one page of 250 blocks, of
which 50 are toggles containing 150 child blocks each, costs **103 separate API calls and over 34
seconds** at 3 req/s (`docs/research/notion-api-practice.md`, the worked-example section, marked
tier **(C)** — a third-party blog, not a vendor statement and not an observation of this project's
code). One page at 19% of the budget is the same finding from outside.

**Consequence for the kill criterion.** *"A warm scan exceeds three minutes on the reference scope"*
cannot be predicted from a resource count, so a first run cannot warn an operator in advance of
exceeding it. Whether that warning is owed is a product question this file does not decide.

## 4. Two ceilings, and one endpoint that is deliberately absent

### 4.1 `POST /v1/data_sources/{id}/query` — 10,000 results, and the ceiling is silent

The query endpoint caps traversal at **10,000 results per query**. At exactly 10,000 rows it returns
**`has_more: false`**, which before `request_status` existed was indistinguishable from a genuinely
complete result (`docs/research/notion-api-practice.md` §4.3). ADR-0006 decision 1's positive test
covers it now: the scan checks for `request_status.type === "incomplete"` on every response and
treats absence as uninformative.

**A `UNQ001` or `REQ001` scope over a data source larger than 10,000 rows cannot be enumerated in one
query.** Partitioning by filter is the only documented route past it, and partitioning requires a
property suitable for partitioning. Neither `REQ001` nor `UNQ001` may report over a scope it
enumerated past this ceiling without the residual register naming the shortfall.

### 4.2 `GET /v1/blocks/{id}/children` — no ceiling, and no signal either

The traversal spine has no documented cap and no truncation signal. It is the reason every rule in
§1 carries `unattested` and the reason ADR-0013 exists. A permission-filtered child list and a
complete one both return `has_more: false`.

### 4.3 `POST /v1/search` is not in this map, and its absence is a decision

**ADR-0014 decision 1: v0.1 calls `POST /v1/search` from no command path.** It is stated here rather
than omitted, because omission is what produced #24 — ADR-0007 opened five design surfaces, found
every one silent on search, and could not tell silence from a negative. **This map was named inside
one of those five**, as the artifact that would enumerate the shipping rules' fetch depths. It is
now explicit instead of silent.

Search is the one endpoint this project classifies as `attested`
(`slice/notion-port.ts`, `ATTESTED_ENDPOINTS`). That classification stands and is not a reason to
call it: an attested endpoint the product does not call contributes no coverage.

## 5. Revisit if

**The request budget changes.** §2. Either input invalidates §3 entirely.

**`REF001` stops being load-bearing.** If Notion ships an endpoint that enumerates a connection's
grant, coverage no longer rests on link resolution, and the nested-block descent in §1.2 — the term
§3.3 identifies as budget-deciding — becomes optional rather than required. Not announced, and it is
also ADR-0002's and ADR-0014's Revisit-if.

**A rule's evidence sufficiency turns out to depend on hydration *order* rather than depth.** Then
this is a sequencing spec, not a depth map, and its shape is wrong. #18 pre-registered this and it
has not fired.

**A second run is observed.** §3.2 validates the formula against one call log. A second run at a
different shape either confirms the formula or replaces §3.3 with something better than
extrapolation.

**`request_status` is observed on any endpoint, on either branch.** Neither `complete` nor
`incomplete` has been seen anywhere. Its arrival changes what `unattested` means in §1 and is
ADR-0006's and ADR-0007's standing Revisit-if.
