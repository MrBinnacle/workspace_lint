**1 — PARTIAL.** All nine values confirmed in xccdf-1.1.2.xsd. Schema order: pass, fail, error, unknown, notapplicable, notchecked, notselected, informational, fixed.
STRUCTURAL ERROR: XCCDF 1.1.2 has NO per-value docstrings. The enumerations are bare (`<xsd:enumeration value="pass"/>`). All descriptive text is one block `xsd:documentation` on the simpleType. Do not present these as per-value annotations.
Verbatim block: "Allowed result indicators for a test, several possibilities: pass= the test passed, target complies w/ benchmark / fail= the test failed, target does not comply / error= an error occurred and test could not complete, or the test does not apply to this plaform / unknown= could not tell what happened, results with this status are not to be scored / notapplicable=Rule did not apply to test target / fixed=rule failed, but was later fixed (score as pass) / notchecked=Rule did not cause any evaluation by the checking engine (role of "unchecked") / notselected=Rule was not selected in the Benchmark, and therefore was not checked (selected="0") / informational=Rule was evaluated by the checking engine, but isn't to be scored (role of "unscored")".
CORRECTIONS: `error` is truncated by the scout — the source continues "or the test does not apply to this plaform" (sic, "plaform" is a typo IN the schema; reproduce it or use [sic]). `notchecked` continues "(role of "unchecked")". `notselected` continues "(selected="0")". Scout omitted the pass/fail/informational/fixed text.
XCCDF 1.2 (xccdf_1.2.xsd, line 3580): same nine values, no additions or removals, but every value now carries its own annotation and ALL text is rewritten. Example — 1.2 `notchecked`: "The <xccdf:Rule> was not evaluated by the checking engine. This status is designed for <xccdf:Rule> elements that have no check." 1.2 `unknown`: "The testing tool encountered some problem and the result is unknown." If you quote 1.1.2 wording you must label it 1.1.2; it is not the current wording.
URL: https://csrc.nist.gov/schema/xccdf/1.1.2/xccdf-1.1.2.xsd and https://csrc.nist.gov/schema/xccdf/1.2/xccdf_1.2.xsd

**2 — PARTIAL. The load-bearing negative survives, but the stated form is too strong.**
Enums confirmed byte-exact. finding-target `status/@state` (id `oscal-finding-target-status-state-values`): only `satisfied` ("The objective has been completely satisfied.") and `not-satisfied` ("The objective has not been completely satisfied, but may be partially satisfied."). observation `@type`: ssp-statement-issue, control-objective, mitigation, **finding** (deprecated 1.1.4 — scout omitted it), discovery, historic. risk status: open, investigating, remediating, deviation-requested, deviation-approved, closed. All exact.
I grepped the raw 148KB metaschema for: not-applicable, notapplicable, not assessed, unable, inapplicable, not-tested, notchecked, unknown, informational, indetermin, no-evidence, out-of-scope. Only three hits, none an assessment outcome: (a) `observation/@method` value `UNKNOWN` — "This is only for use when converting historic content to OSCAL, where the conversion process cannot initially identify the appropriate method(s)." That is the METHOD, not the result. (b) CVSS facet vocabularies imported from FIRST (`not-defined`, `unknown`, `unavailable`) — scoring metadata, not outcomes. (c) "Any subjects not identified in this way are out-of-scope." — subject selection prose, not a status value.
TWO QUALIFICATIONS you must state, or the negative is overclaimed: (i) `status/@state` is the ONLY closed enum here — no `allow-other`. But observation `@type` and risk status BOTH carry `allow-other="yes"`, so a producer may emit its own token; OSCAL does not forbid an "unassessed" value, it merely does not define one. (ii) finding-target has a sibling flag `reason` with `allow-other="yes"` and values pass / fail / **other** ("Some other event took place that is not a pass or a fail."), plus remarks "Reason may contain any value". That is the nearest thing OSCAL has to an escape hatch.
Safe formulation: "OSCAL defines no outcome value for not-assessed, not-applicable, or unable-to-assess. The binary `satisfied`/`not-satisfied` state is closed; the adjacent `reason` and `type` vocabularies are open, so the gap is a definitional absence, not a prohibition."
URL: https://raw.githubusercontent.com/usnistgov/OSCAL/main/src/metaschema/oscal_assessment-common_metaschema.xml

**3 — MISATTRIBUTED. Wording exact, requirement level wrong.** Both quoted strings appear verbatim in 6.5.1 — but in the SECOND list, introduced by "The audit report **can also** include or refer to the following, **as appropriate**:". They are optional dash-bullets, not requirements. The mandatory list is the lettered a)–k) set under "should include or refer to". The claim that 19011 "requires the audit report to include" these is false. Verbatim: "— any areas within the audit scope not covered including any issues of availability of evidence, resources or confidentiality, with related justifications;" and "— a summary of the audit process, including any obstacles encountered that may decrease the reliability of the audit conclusions;". Use "may include, as appropriate".

**Attribution problems**
- Claims 3/4/5: the synersia.org PDF is a complete, unaltered reproduction of ISO 19011:2018 including the intact ISO copyright page — "© ISO 2018. All rights reserved… no part of this publication may be reproduced… including photocopying, or posting on the internet or an intranet, without prior written permission." Posting it is exactly what that clause forbids. It is an unauthorised copy. The wording and the clause numbers (3.5, 6.5.1, items a–k) are genuine and I verified against it, but the citation must read "ISO 19011:2018, clause 6.5.1" with no URL, or link to the ISO catalogue page. Do not cite synersia.org in the design document.

- Claims 6/7: the squarespace-hosted PDF is also an unofficial mirror. Cite "ISA 705 (Revised), para. 5(a)" and "para. 17" and point at IAASB.
